# 模型生命周期与 AI 运维主机 Agent 设计

日期：2026-08-17
状态：已确认，待实施

## 1. 目标

本次改动补齐 DGX Spark Web Manager 的两个管理闭环：

1. 模型库可以安全地永久删除不再需要的 Hugging Face 或本地模型。
2. 部署实例可以停止以释放设备资源，也可以卸载并删除不再需要的推理服务。
3. AI 运维助手可以连续采集真实服务器状态、分析异常，并在批准后直接操作宿主机 Shell 完成部署或修复。
4. 只读诊断可以自动执行；所有改变系统状态的操作必须先在面板中确认。

功能继续面向单台 DGX Spark，保持 ARM64 原生运行、Ant Design 前端、移动端适配和深色模式支持。

## 2. 已确认的产品决策

- Shell 权限采用“低风险自动执行，高风险确认”。
- 自动执行只适用于后端定义的结构化只读工具，不能由 AI 自行声明某条 Shell 为低风险。
- 任意原始 Shell 都必须审批，即使命令看起来只读。
- 宿主机执行采用独立的 root `systemd` Agent，通过 Unix Socket 与管理器通信。
- 停止实例只释放运行资源，不删除部署配置或模型文件。
- 卸载服务删除推理容器、网关路由和部署记录，但不顺带删除模型。
- 永久删除模型是独立动作；存在基础模型或 Draft Model 引用时必须阻止删除。
- 管理器创建的容器和扫描发现的推理容器都允许卸载，后者使用更高风险确认。

## 3. 当前问题

### 3.1 模型生命周期不完整

`GET /api/models` 目前只有列表能力。发现服务在磁盘目录消失后把记录标记为 `unavailable`，但面板不能主动删除文件，也不能清理不再需要的历史记录。

### 3.2 部署删除能力没有形成完整语义

后端已经支持停止和删除管理器创建的容器，前端也有删除入口，但动作仍称为“删除部署”，扫描发现的推理容器被硬性禁止删除。界面没有把“停止以卸载模型资源”和“永久移除服务”清楚地区分。

### 3.3 AI 助手真实链路不稳定且能力受限

现有 Provider 测试只请求 `/models`，不能证明配置的默认模型能够完成诊断请求。实机探测显示当前 Provider 对 `/chat/completions` 返回 HTTP 200，但推理内容会消耗现有的 512 Token 上限，响应可能以 `finish_reason=length` 结束，最终 `content` 为空或 JSON 被截断。

诊断服务还是一次性请求，只允许启动、停止、重启部署和扫描资产，并在系统提示中明确禁止 Shell。因此它既无法通过多轮检查缩小故障范围，也无法完成安装依赖、修复配置或执行部署等用户期望的工作。

## 4. 总体架构

系统增加三个相互独立但可组合的领域能力：

1. `ModelLifecycleService` 负责模型删除预检、异步删除、引用保护和发现同步。
2. `OpsOrchestrator` 负责运维会话、Provider 调用、结构化工具循环、审批计划和结果总结。
3. `dgx-spark-ops-agent` 作为宿主机 root 服务执行只读工具和已批准的 Shell 作业。

FastAPI 管理器仍然是唯一对浏览器开放的服务。浏览器不能直接访问主机 Agent；第三方 AI Provider 也不能直接访问 Agent、Docker Socket、凭据或宿主机网络接口。

## 5. 模型删除

### 5.1 API 与任务

新增 `DELETE /api/models/{model_id}`。请求必须携带模型名称确认值，API 通过 CSRF 和管理员会话鉴权，然后创建 `model.delete` 异步任务。

API 创建任务前执行一次预检，任务真正开始删除前再次执行相同预检。第二次检查用于阻止“用户确认删除后、任务执行前又新建部署”产生的并发误删。

删除任务使用 `model:{id}:delete` 幂等键。同一模型不能同时下载、删除或被新的部署任务引用。模型进入 `deleting` 状态后，部署预览和创建 API 都拒绝使用它。

### 5.2 引用检查

以下任一情况存在时，删除返回冲突并列出引用它的部署：

- `Deployment.model_id` 等于目标模型 ID；
- 已保存部署配置中的 Draft Model ID 等于目标模型 ID；
- 兼容旧记录时，基础模型路径或 Draft Model 路径解析后等于目标模型路径。

检查覆盖运行中、已停止、不健康和正在变更的全部部署，不能只检查健康实例。

### 5.3 Hugging Face 模型

Hugging Face 模型不能直接删除 snapshot 目录。任务先运行：

```text
hf cache rm model/<repository_id> --cache-dir <configured-cache> --dry-run --json
```

预检输出用于确认删除目标和预计释放空间。正式执行使用相同目标并增加 `--yes`。这样由 `huggingface_hub` 处理 refs、snapshots 和共享 Blob，避免破坏其他缓存仓库。

命令以参数数组运行，不经过 Shell。仓库 ID必须重新通过现有校验器，缓存目录必须等于配置的 Hugging Face 根目录。

### 5.4 本地模型

本地模型删除前必须同时满足：

- 目标路径真实解析后位于配置的模型根目录内；
- 目标不是模型根目录本身；
- 目标不是穿过边界的符号链接；
- 目标与数据库记录的规范化路径一致；
- 目标当前未被任何部署引用。

删除使用 Python 文件系统 API，并在递归前后重新验证边界。不能把数据库路径拼接到 Shell 命令。

### 5.5 记录与失败恢复

- `available` 模型删除成功后移除 `ModelAsset` 记录并触发模型扫描。
- 文件已经不存在的 `unavailable` 模型只删除历史记录。
- 删除过程中失败时保留模型记录，状态改为 `delete_failed`，任务日志保存脱敏错误。
- 任务结果记录实际释放字节数、删除来源和重新扫描结果。
- 审计事件记录操作者、模型 ID、仓库 ID、来源、结果和任务 ID，不记录 Provider/Hugging Face Token。

## 6. 部署实例停止与服务卸载

### 6.1 停止实例

现有 `stop` 动作在界面统一命名为“停止实例”。它停止推理容器并释放 GPU/统一内存，但保留容器、部署参数、网关别名和模型文件。再次启动时继续复用原容器。

停止开始后，部署先进入 `stopping` 状态，网关立即停止把新请求路由到该实例。容器停止成功后状态变为 `exited`。

### 6.2 卸载模型服务

现有 `delete` API 保持兼容，但界面和任务标题统一使用“卸载服务”。执行顺序为：

1. 将部署状态设为 `deleting`，从健康网关路由中移除；
2. 按容器 ID重新获取并验证容器身份；
3. 停止仍在运行的容器；
4. 删除容器；
5. 删除部署记录；
6. 重新扫描容器并记录结果。

模型文件始终保留。用户之后可以从模型库单独删除模型。

### 6.3 扫描发现的容器

扫描发现且 `managed=false` 的 vLLM/SGLang 容器也允许卸载，但必须满足：

- 容器仍符合推理运行时识别规则；
- 容器 ID 和名称与部署记录一致；
- 目标不是管理器自身或主机 Agent；
- 用户在高风险确认中输入容器名称。

界面明确提示该容器不是由面板创建，删除后无法由保存的部署参数自动恢复。执行仍只删除目标容器，不删除镜像、卷或模型目录。

### 6.4 失败语义

容器停止或删除失败时保留部署记录和最后错误，不能先删数据库记录。容器已经不存在时，卸载动作清理陈旧部署记录并返回“容器已不存在”的成功结果。

## 7. AI 运维会话

### 7.1 会话模型

新增以下表，不修改现有表结构，避免对当前 SQLite 数据库执行破坏性迁移：

- `OpsSession`：标题、Provider、可选目标部署、状态、创建者和时间戳；
- `OpsMessage`：会话、角色、正文、脱敏元数据和时间戳；
- `OpsToolRun`：会话、工具、参数摘要、风险、状态、输出摘要、Agent 作业 ID和时间戳。

高风险变更继续使用现有 `OperationPlan` 存储审批状态和结构化步骤。消息元数据只保存关联的 plan ID，不向旧表添加列。现有历史诊断方案继续显示并可查询。

### 7.2 Provider 真实能力探测

Provider 测试分成两层：

1. `/models` 检查 Base URL、鉴权和基本兼容性；
2. 使用所选默认模型发送一个极小的 `/chat/completions` JSON 探测，检查状态码、`choices`、最终 `content` 和结束原因。

界面分别显示连接状态与默认模型状态。默认模型不存在、响应为空、只返回推理字段或输出被截断时，错误必须包含可操作原因。

### 7.3 兼容推理模型的响应处理

运维请求使用足够容纳推理和最终 JSON 的输出预算。初次请求使用受配置上限约束的较大预算；出现 `finish_reason=length`、空 `content` 或不完整 JSON 时，执行一次修复重试：

- 缩短已观察上下文，只保留相关工具摘要；
- 明确要求只返回最终 JSON，不返回分析过程；
- 提高输出预算但不超过系统硬上限；
- 把解析错误作为修复输入，而不是静默失败。

如果 Provider 拒绝 `response_format`，在确认是参数兼容错误后重试一次不带该字段的严格 JSON 提示。`reasoning_content` 只用于判断响应行为，不作为可执行内容，也不保存或展示模型隐式推理过程。

### 7.4 工具循环

每轮 AI 只能返回受 Pydantic Schema 约束的下一个动作：

- 调用一个结构化只读工具；
- 生成需要审批的变更计划；
- 返回最终诊断或追问用户。

后端验证工具名和参数后执行，再把脱敏、截断的结果反馈给 Provider。单次用户请求限制最大工具轮数、总耗时、单次输出和累计输出；达到限制后停止并说明原因。

第一版自动只读工具包括：

- 主机版本、运行时间、CPU、内存、磁盘和 GPU 摘要；
- Docker 容器列表、inspect、stats 和受限行数日志；
- `systemd` 服务状态和受限行数 journal；
- 监听端口和进程摘要；
- 管理器数据库中的模型、部署、任务和网关健康摘要；
- 指定白名单配置文件的只读元数据，不向 AI 返回密钥或完整环境变量。

这些工具由后端映射到固定可执行文件和参数数组。AI 不能提供二进制路径、Shell 运算符、重定向或任意环境变量。

## 8. 宿主机 Agent

### 8.1 安装与运行

仓库提供幂等安装脚本，在 DGX Spark 上创建：

- `dgx-spark-ops-agent.service`；
- `dgx-spark-ops-agent.socket`；
- 专用 `dgx-spark-ops` 系统组；
- `/run/dgx-spark-manager/ops-agent.sock`；
- `/etc/dgx-spark-manager/ops-agent.key`；
- Agent 作业和日志目录。

Agent 以 root 运行，以便在用户批准后安装软件、写系统配置和管理服务。它使用宿主机 ARM64 Python，不下载或模拟 x86 运行时。管理器容器只读挂载 Socket 和认证密钥，并加入专用 Socket 组。

### 8.2 协议认证

管理器与 Agent 使用版本化 JSON 协议。每个请求包含协议版本、请求 ID、时间戳、随机 nonce、动作、参数和审批声明，并使用随机安装密钥进行 HMAC-SHA256 签名。

Agent 拒绝：

- 签名错误或字段不完整的请求；
- 超出允许时间窗口的请求；
- 重复 nonce；
- 未知协议版本或动作；
- 缺少审批 ID的原始 Shell 和写操作。

Unix Socket 不暴露 TCP 端口，权限为 `root:dgx-spark-ops 0660`。认证密钥不写入数据库、任务日志或 AI 上下文。

### 8.3 作业执行

结构化只读工具直接使用参数数组执行，并设置短超时。已批准的原始 Shell 通过固定的 `/bin/bash -lc` 入口执行，参数包含：

- 精确命令；
- 受验证的工作目录；
- 超时；
- plan ID、步骤 ID、批准人和批准时间；
- 可选的非敏感环境变量白名单。

长操作作为 Agent 作业运行。管理器轮询状态并把增量输出写入任务日志；支持取消、超时和进程组终止。输出设置单作业上限并在写入数据库前执行密钥、Token、Authorization Header 和常见凭据格式脱敏。

Agent 不接受交互式 PTY，不响应密码提示，也不允许请求方覆盖 `PATH`、动态链接器变量或 Agent 自身环境。

## 9. 风险分类与审批

只有结构化只读工具可以自动执行。以下动作始终进入 `OperationPlan`：

- 任意原始 Shell；
- 创建、修改或删除文件；
- 安装、升级或卸载软件；
- 创建、停止、重启或删除服务和容器；
- 下载、部署或删除模型；
- 修改网络、用户、权限、防火墙、驱动或系统启动项。

每个待批准步骤包含命令或结构化动作、目标、原因、预期影响、风险、超时、验证方法和回滚方案。审批后步骤内容不可变；任何修改都生成新计划并重新审批。

用户拒绝计划后不会执行任何步骤。多步骤计划在中途失败时停止后续步骤，执行已提供的自动验证，并把可用回滚方案展示给用户；不会未经再次确认自动执行高风险回滚 Shell。

## 10. 前端交互

### 10.1 模型库

桌面表格和移动记录都增加删除图标按钮。确认弹窗显示模型来源、路径或仓库、大小、引用实例和不可逆提示。永久删除要求输入完整模型名称。

删除任务创建后跳转或链接到任务详情，并立即刷新模型状态。引用冲突在弹窗内列出可点击的部署实例。

### 10.2 部署实例

动作统一为“启动”“停止实例”“重启”和“卸载服务”。卸载确认明确说明模型文件会保留。扫描发现的容器使用更醒目的高风险说明并要求输入容器名称。

### 10.3 AI 运维助手

页面使用 Ant Design 构建三部分：

- 顶部紧凑选择区：Provider、目标部署和新建会话；
- 会话时间线：用户消息、助手结论、自动只读工具及折叠结果；
- 审批与执行区：命令、影响、回滚、批准/拒绝、实时输出和最终状态。

桌面端在可用宽度内显示会话与计划详情，移动端改为单列抽屉。命令输出采用固定尺寸、可滚动的终端区域，不因动态内容造成布局跳动。所有颜色使用现有主题变量，完整支持浅色和深色模式。

## 11. 错误处理与审计

- Provider、编排器、Agent 和具体命令错误使用不同错误码，前端显示发生层级。
- Agent 不可达时只禁用服务器工具执行，历史会话和纯 AI 说明仍可查看。
- 工具输出和命令日志统一脱敏；检测到疑似凭据时用占位符替换。
- 每次自动工具调用、计划创建、审批、拒绝、执行、取消和失败都写入审计。
- 审计保存参数摘要和结果摘要，不保存 Provider Key、HF Token、Cookie、完整环境或未脱敏日志。

## 12. 安装、升级与回滚

安装流程先部署并验证主机 Agent，再更新管理器 Compose 挂载，最后更新 Web Manager。升级脚本在重启前验证 Agent 协议版本、Socket 权限和健康探测。

回滚时可以先从 Compose 移除 Agent 挂载并恢复上一版管理器镜像，再停用 Agent Socket 和 Service。模型、部署、Provider、历史诊断和新增运维会话数据均保留。Agent 不可用不得影响 OpenAI 网关和现有推理部署。

## 13. 测试策略

### 13.1 后端

- 模型路径边界、符号链接、根目录保护、HF dry-run 和删除失败恢复；
- 基础模型、Draft Model、旧路径引用和并发部署引用检查；
- 管理与扫描容器卸载、容器消失、身份变化和失败保留记录；
- Provider 默认模型探测、空内容、推理内容、截断 JSON、修复重试和不支持 `response_format`；
- 工具 Schema、轮数/时间/输出限制、风险分类和审批后不可变；
- Agent HMAC、时间窗口、nonce 防重放、Socket 错误和输出脱敏。

CI 使用临时目录、MockTransport、伪 Docker Client 和伪 Agent，不要求 root 或真实删除主机文件。

### 13.2 前端

- 模型删除引用冲突、名称确认、任务反馈和移动端操作；
- 停止与卸载文案、扫描容器高风险确认；
- Provider 真实探测错误、会话工具时间线、审批、拒绝和实时输出；
- 桌面、移动、浅色和深色模式下无溢出和重叠。

### 13.3 DGX Spark 验收

- 在 ARM64 DGX Spark 安装并启用 Agent，验证 Socket 权限和重启恢复；
- 自动执行 GPU、内存、Docker、日志和服务只读诊断；
- 生成一个写操作方案，确认审批前未执行、审批后成功执行并完整审计；
- 用测试模型验证停止、卸载服务、HF 删除、本地删除和引用阻止；
- 使用当前配置的第三方 Provider 验证推理模型响应不再因 512 Token 截断而失败；
- 回归 `/v1/models`、chat completions、现有部署和网关健康。

## 14. 验收标准

1. 模型库能够永久删除未引用模型，并正确拒绝删除被基础模型或 Draft Model 使用的模型。
2. 部署页能清楚地区分停止实例与卸载服务，二者都不会误删模型文件。
3. 扫描发现的推理容器可以在高风险确认后卸载。
4. AI 助手能使用当前 Provider 完成真实诊断，不再因空内容或截断 JSON 返回不可用。
5. 助手可自动执行结构化只读检查，并把结果用于后续分析。
6. 任意 Shell 或系统变更在批准前绝不执行；批准后可由主机 Agent 完成部署或修复。
7. 命令、输出、状态和操作者可在面板追踪，并写入脱敏审计。
8. Agent 故障不影响管理面板、OpenAI 网关或已运行的推理服务。
9. 后端、前端、ARM64 构建和 DGX Spark 实机验收全部通过。

## 15. 告警与诊断历史物理清理

系统设置增加危险操作“清除告警与诊断信息”。该操作执行数据库物理删除，不采用隐藏、归档或软删除：

- 删除状态为 `failed` 的历史任务；
- 删除全部诊断与操作计划；
- 删除 AI 运维会话，并级联删除消息、工具调用和工具输出；
- 删除上述记录关联的诊断、运维和失败任务审计明细；
- 保留模型、部署、Provider、API Key、Hugging Face 设置、网关指标和成功任务。

请求必须通过管理员会话和 CSRF 校验，并要求输入完整确认短语 `清除历史记录`。若存在正在排队、运行、暂停或取消中的运维响应/执行任务，或存在已经批准但尚未完成的操作计划，接口返回冲突且不删除任何记录。

清理必须在单个数据库事务中完成。事务最后只新增一条 `maintenance.history.clear` 审计事件，记录操作者和各类删除数量，不保存被删除内容、命令、错误日志或工具输出。前端成功后统一刷新任务、诊断、运维会话、审计和仪表盘查询；失败时保留确认弹窗并显示服务端原因。
